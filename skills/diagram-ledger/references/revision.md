# Revisions with a receipt

Use this workflow when editing an existing diagram. Preserve the owner's IDs, spatial arrangement, meaning, and unrelated styling. A small label edit needs a small contract, not a redesign.

Visual repairs and polish are revisions too. If the previous source was already delivered, capture that source and a new contract before repairing it, even when the user only says “fix the audit findings.” Within an unfinished revision, retain its original baseline and contract while repairing permitted fields. After the last source edit, rerun both the receipt check and visual verification: an earlier passing receipt does not cover a later file.

## Capture → contract → edit → verify

1. **Capture the original before editing.** For an annotated standalone SVG or uncompressed draw.io:
   ```sh
   python3 "<skill-directory>/scripts/revision.py" plan diagrams/content-review-flow/content-review-flow.drawio --out diagrams/content-review-flow/revisions/01/plan
   ```
   This saves an exact baseline, its inventory and SHA-256, and `contract.json`. The command creates its output directory: pass a path that does not exist, without running `mkdir` on that path first. Never overwrite the baseline. If a path already exists, use a fresh one rather than deleting it. Use a new plan directory for each revision.
2. **Write the contract from the user's request, before editing.** Read the snapshot to obtain exact entity keys and values. Every existing field is protected unless explicitly allowed. Add `require` assertions for requested outcomes; permissions alone do not prove the work was done. Keep the contract narrow. Do not loosen it merely to make a failed edit pass. Adding or deleting entities does not need `document:root.content` or `order` permission: the checker already excludes added/deleted entities from the surviving-order comparison. Keep page/title/CSS/footer protected unless the user actually requested those changes.
3. **Edit a separate copy.** Retain IDs when renaming. Add only requested entities/relationships; preserve unaffected geometry, styles, grouping and routing. Grow the page or affected container only if necessary and include those changes in the contract. If the request inherently conflicts with preservation, explain the conflict and propose the smallest additional change.
4. **Compare the final source to the saved baseline.**
   ```sh
   python3 "<skill-directory>/scripts/revision.py" check diagrams/content-review-flow/revisions/01/plan/baseline.drawio diagrams/content-review-flow/content-review-flow-revised.drawio --contract diagrams/content-review-flow/revisions/01/plan/contract.json --out diagrams/content-review-flow/revisions/01/review --require-outcomes
   ```
   Exit 0 = contract passed; 1 = unexpected changes, unmet outcomes or unused allowances; 2 = invalid/unsupported input. `--require-outcomes` rejects an empty `require` list before producing a receipt; use it for requested revisions, including visual polish. Without this flag, the utility still supports preservation-only comparisons, which do not prove the requested work occurred. All comparisons produce JSON and a self-contained HTML receipt except invalid-input errors. Receipts retain exact before/after sources and the contract. Use a fresh output directory on each retry so evidence is not overwritten. Unused permissions fail the check because they weaken preservation. Remove unused permissions (narrowing the original contract is safe); do not edit unrelated content just to use them.
5. **Render and inspect both sources.** Check geometry, labels and arrowheads using the format's normal verification workflow. A contract pass only verifies the fields it covers. It cannot validate an incorrect user-intent interpretation or replace visual review.
6. **Deliver the revised editable source and receipt.** Summarize requested changes, preserved content, checks performed, assumptions and any unsupported checks. Do not call a revision verified if requirements are empty or the visual check was skipped; describe the narrower check that ran.

## Contract format

`plan` creates the exact baseline hash. Edit its `intent`, `allow` and `require` values. Example for a rename plus a connection in draw.io:

```json
{
  "version": 1,
  "baseline_sha256": "use the hash generated by plan",
  "intent": "Rename intake; connect it to the existing archive",
  "allow": {
    "node:main/intake": ["label"],
    "edge:main/archive-link": ["added"]
  },
  "require": [
    {"entity": "node:main/intake", "field": "label", "equals": "Validated intake"},
    {"entity": "edge:main/archive-link", "field": "source", "equals": "intake"},
    {"entity": "edge:main/archive-link", "field": "target", "equals": "archive"}
  ]
}
```

Entity keys are `node:PAGE/CELL`, `edge:PAGE/CELL`, or `layer:PAGE/CELL` for draw.io; a bare `mxGraphModel` uses page name `page`. SVG uses `node:ID`, `edge:ID`, `container:ID`. `document:root` protects the remaining document. IDs are case-sensitive. The snapshot is authoritative.

Allowed fields: `label`, `geometry`, `style`, `membership`, `source`, `target`, `content`, `order`; `added`/`removed` permit whole-entity addition/removal. No wildcards. `content` covers remaining XML, including identity and attributes not classified elsewhere. `document:root.content` covers page properties, SVG definitions/CSS, title/footer/background and unannotated content. `document:root.order` detects changed stacking order among surviving annotated SVG entities or draw.io cells. Attribute order and indentation are ignored; style strings, path data and numerical spellings are deliberately compared exactly.

Each required outcome is either `{"entity":"…","exists":true|false}` or `{"entity":"…","field":"…","equals":VALUE}`. Values must match the snapshot's JSON type. SVG `label` is the concatenated text of the annotated group, including secondary captions; draw.io `label` is its raw `value` (which may contain HTML). Geometry/style/membership assertions use their full snapshot values. For a new edge, require its endpoints and label, not merely its existence. For deletion, require `exists:false`.

## Coverage and limits

- **draw.io:** every page and cell, stable IDs, parents, endpoints, geometry including waypoints, styles and remaining XML. Unsupported compressed diagrams and wrapper objects stop with an error; export uncompressed XML to a new file before taking the baseline. Parent cycles and dangling references fail. Native rendering is still required.
- **SVG:** use sibling groups annotated with `data-node="ID"`, `data-edge="ID" data-from="SOURCE" data-to="TARGET"`, and `data-container="ID"`. Declare grouping with `data-within` / `data-outside`; the renderer separately measures it. Nested annotated groups are rejected. All remaining XML is protected as document content. Declared endpoints are compared, not inferred from a path's pixels. Do not add annotations after capturing a baseline to disguise other edits.
- **Excalidraw, unannotated SVG, HTML and Mermaid:** retain the original, review a source diff, inventory IDs/relationships manually, render both versions with their native renderer and deliver a plain-language change log. State that automated field preservation was unavailable. Do not convert the source just to obtain a green receipt. For Excalidraw, preserve seeds and two-way label/arrow bindings as well as IDs, geometry and grouping; see its [format guide](excalidraw.md).

The receipt is evidence of a particular contract and file pair, not a cryptographic signature, security sanitizer or proof of correctness. Review the allowed changes alongside the user request. Do not rerun `plan` on the edited file to erase failures.

**Beta application imports:** a draw.io receipt covers the source sent toward Lucidchart, not the document Lucidchart creates. Capture a fresh export if the user has edited in Lucidchart. SmartDraw VSON and native SmartDraw documents require retained sources and a manual change log; the automatic receipt does not cover them.
